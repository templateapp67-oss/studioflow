Do not paste API keys or signing secrets into this chat, GitHub, SQL, frontend `VITE_*` variables, or screenshots. Add them directly in the Supabase Dashboard.

Supabase normally provides `SUPABASE_URL`, `SUPABASE_ANON_KEY` and `SUPABASE_SERVICE_ROLE_KEY` to Edge Functions. Keep the service-role key server-only. Do not replace, rotate, or copy the existing production Razorpay credentials. The payment function update must retain the current live Razorpay configuration; a separate test environment must use its own test credentials.

Two more secrets are added only after their respective hooks are created:

- `RESEND_WEBHOOK_SECRET`: the signing secret returned by the new Resend webhook.
- `SEND_EMAIL_HOOK_SECRET`: the separate signing secret generated by the Supabase Auth Send Email Hook. This is **not** the Resend webhook secret.

## 4. Supabase Auth OTP settings

The code keeps Supabase Auth as the identity authority. It does not create a parallel OTP table or mint login sessions itself.

In NEW FINAL TEMLETE APP → Authentication → Providers → Email:

- Keep email provider enabled.
- Set Email OTP Expiration to **600 seconds (10 minutes)**.
- Keep email confirmation enabled for signup.
- Review the provider's OTP/email request rate limits.

After the Auth Hook function is deployed, go to Authentication → Hooks → Send Email Hook. Configure the HTTPS hook URL:

`https://zilwgiuiygqqardzutxi.supabase.co/functions/v1/studioflow-auth-email-hook`

Generate the hook secret in Supabase, then save that exact value as `SEND_EMAIL_HOOK_SECRET` in Edge Function secrets. Enable the hook only after the function is deployed and the secret is present. The function handles the documented Supabase Auth signup OTP, magic-link, recovery, invite, email-change and security-notification actions.

## Deployment safety for the existing live project

The target project is active and already serves the application. It currently has active functions named `studioflow-booking-emails` (version 7) and `studioflow-payments` (version 91).

Deploying a function with either existing name replaces the live version immediately. Therefore:

- Do not deploy either modified function until the owner explicitly approves the production cutover.
- Deploy the new uniquely named functions only after their secrets and SQL objects are ready, and only with approval.
- Preserve the existing Razorpay credentials, WhatsApp integrations, payment webhooks, booking records and current email behavior until the cutover is approved.
- The source changes are on the feature branch only; no merge or live deployment has occurred.

The target project's migration history was read-only checked through `20261127130400`; the proposed migration version `20261127140000` sorts after it. The three proposed email tables were absent at the time of that check. Recheck migration history and table existence immediately before applying the SQL.

## 6. Retry schedule

The retry function is protected by `EMAIL_RETRY_WORKER_TOKEN` in the `x-email-worker-token` header. After it is deployed, configure a Supabase scheduled Edge Function invocation every 5 minutes:

- Method: POST
- URL: `https://zilwgiuiygqqardzutxi.supabase.co/functions/v1/studioflow-email-retry`
- Header: `x-email-worker-token: <the same EMAIL_RETRY_WORKER_TOKEN>`
- Body: `{}`

Do not expose this token in browser code. Deploy the retry function with JWT verification disabled only because it authenticates using this independent server-only token.

## 7. Verification before production

Run the following end-to-end checks on the target project:

1. Booking confirmation for an ordinary salon appointment.
2. Booking confirmation for home service (address and instructions).
3. Razorpay test-mode deposit payment; receipt only after the payment is captured and booking is settled.
4. Supabase Auth signup: six-digit OTP, expiry after 10 minutes, wrong-code rejection, resend and valid verification.
5. Resend webhook: delivered, hard bounce, failed, complaint, invalid signature and duplicate event replay.
6. Retry worker: temporary send failure is retried with the same idempotency key; hard bounce/complaint address is not sent again.
7. Booking and payment remain complete if email delivery fails.
8. Tenant ownership checks still prevent one salon/customer from sending another tenant's booking email.

The current payment schema supports the existing booking advance/payment order. It does not provide a multi-payment split ledger for a booking; the receipt will report the actual recorded amount paid and remaining balance rather than invent split/payout data.
