# Booking availability repair: rollout review

## Status and scope

The migrations below are **release-pending, not applied or approved for production**. The application and database changes must be released together: the directory's branch-aware practice booking calls a new RPC that does not exist until the first migration is applied.

1. `20261127140001_booking_slot_availability_repair.sql` unifies the published website, customer directory and men's booking availability, records branch-schedule provenance, guards active-service assignments and adds the authenticated branch practice-booking wrapper.
2. `20261127140100_iron_ink_availability_ist.sql` follows the first migration and repairs Iron Ink's separate, unpaid tattoo-request flow. It replaces the branch availability RPC only when the optional Iron Ink branch feature is already installed; it does not install that feature.

The earlier, unrelated `20261127140000_studioflow_resend_transactional_email.sql` is recorded as applied to production in the release ledger. Recheck the target's migration history before any release; this booking work did not apply it.

The original failures combined stale staff-to-service IDs, inconsistent IST/weekday and branch-schedule handling, and storefront actions that could substitute an unrelated service or present example slots as live. Stale-only assignments now fall back to all active catalogue services; any remaining active assignment is still restrictive. This is a compatibility rule, not evidence of a specialist's qualifications. Owners should review stale assignments and explicitly select the services their staff can perform. Distinct service IDs are never merged merely because their names match.

## Deployment implications

- Old branch-shift rows could have been copied from business hours or projected to every branch. The first migration preserves them but labels previously unattributed rows `legacy` and does not treat them as proof of a shift. A read-only production snapshot during this review found existing shift rows across multiple tenants; the current count and affected availability may differ. A valid personal schedule can still establish a single-location shift, and explicitly saved workspace/direct shifts remain usable. Coordinate with owners to confirm genuine branch schedules before rollout. This also affects availability checks for new or rescheduled owner bookings.
- Adding `schedule_source`, updating existing rows, and setting it `NOT NULL` can take table locks and generate writes; plan and monitor an appropriate maintenance window. No booking rows are deleted by these migrations.
- The older optional `nexora_customer_booking_options` RPC is patched only if its expected definition is present; an unexpected body fails the migration rather than silently changing its eligibility logic. The production definition matched the expected patterns at review time. Its existing `public.services` versus `public.salon_services` ID mismatch remains unresolved; do not infer a mapping by name or across tenants. Verify that separate normalized path before depending on it.
- Production did not have the optional Iron Ink branch RPC at review time. If that optional historical feature is installed later, its older definitions can overwrite this repair; prepare and review a new forward migration that reapplies the branch-aware repair after the feature is installed.
- Existing practice-booking receipts without a request fingerprint remain stored, but cannot be replayed using the same request key. The branch-aware practice RPC requires authentication and writes only isolated zero-price demo records. Public template previews instead use illustrative times and cannot write or initiate payment. Iron Ink requests are separate and unpaid.

## Recommended release gates

1. Recheck migration history, function definitions/signatures, table columns, triggers and role grants against the target environment. Capture a database backup and the current function/trigger definitions and ACLs for a reviewed forward rollback. Do not alter migration history or blindly drop the provenance column to roll back.
2. In a disposable PostgreSQL environment representative of the target schema, apply both migrations in order, including the optional branch variant if applicable. Use synthetic tenants to check owner and guest RLS, explicit branch isolation, hours and staff assignments, retired services, bundles/coupons, practice bookings, request retries and unpaid Iron Ink requests. Test competing writes from separate database sessions; the offline PGlite checks are sequential and do not prove concurrency safety. The connected QA project was empty during this review and was not migrated.
3. After separate human approval, use the protected manual migration/deployment workflow. Confirm the database migration succeeds before serving the matching client, then monitor availability, owner scheduling and errors. Exercise payment only in an approved sandbox; do not create real bookings or payments as a smoke test without authorization.

Both files are transactional and were applied twice in disposable PGlite fixtures, including the optional Iron Ink branch variant. The offline role tests check that guest reads do not expose booking rows, new internal engine/trigger helpers are not executable by browser roles, and the new practice write is authenticated. Existing public read entry points remain role-scoped; neither repair widens table RLS policies. These checks are not a production dry-run, a live-browser test, or proof of real PostgreSQL concurrent-write behavior.
