# StudioFlow authentication and access rollout

The source targets Supabase project `zilwgiuiygqqardzutxi`. Existing owners, staff and customers keep their Supabase identities. Supabase Auth stores salted bcrypt hashes. StudioFlow delegates signup, login and resets to Supabase Auth. New and changed passwords require at least 12 characters in the web UI and local Auth configuration. Existing passwords remain valid under Supabase Auth's login behavior.

Owners, staff and customers can enroll a TOTP authenticator under **Account security**. Once a factor is verified, the user must complete two-step verification to access private data and protected operations. Enrollment is optional. The recovery UI uses the same MFA challenge for an enrolled account, and it also offers a **recovery-code** path: the Account security screen can generate a show-once batch of backup codes (hashed with SHA-256 + per-code salt before storage, single-use). Consuming a code opens a 10-minute window in which the account may use authenticated surfaces while setting up a fresh authenticator. An account holder who loses their authenticator and has no recovery code should contact the project's support operator for identity-verified recovery.

## Deploy to the linked project

1. Compare the project's migration history to the ZIP before applying pending migrations. The MFA migrations are `20261125100000_studioflow_auth_access_hardening.sql` and `20261126143000_studioflow_mfa_recovery_codes.sql`. The new one depends on the first (it replaces `studioflow_private.mfa_session_allowed()`), on the shared Edge rate-limit migration `20261117061129_studioflow_shared_edge_rate_limits.sql` (its consume RPC throttles per account), and on `pgcrypto` (in the `extensions` schema) for `digest()`. Both are recorded as release-pending in `docs/integrations/restored-supabase-history.json`; apply them only through the protected manual production migration workflow, after `20261125100000` has landed. Check any existing `pgrst.db_pre_request` setting for the `authenticator` role before rollout. If present, preserve its checks alongside the new hook.
2. In hosted Supabase Auth, enable TOTP enrollment and verification. Set the hosted minimum password length to 12. Configure Auth rate limits for sign-up/sign-in and token verification to match the ZIP’s configured values of 25 and 20. Hosted Auth settings are separate from the SQL migration and local `config.toml`.
3. Coordinate the migration with deployment of the web app and API. The staff invite mail handler uses the new scoped RPC. Set the existing server-side Supabase service credential for the shared quota counter. For custom storefront origins that send staff invite email, list the HTTPS origins in `STUDIOFLOW_STAFF_INVITE_ORIGINS`, separated by commas.
4. After merging, run the GitHub Production workflow on main with `apply_and_deploy`. Its protected release applies pending migrations, deploys the changed Edge Functions with their shared helper, and releases the website. The changed functions are `studioflow-payments`, `nexora-mobile-qr`, `studioflow-service-ai-images`, `studioflow-campaign-whatsapp`, `studioflow-welcome-whatsapp`, `nexora-whatsapp-connect` and `studioflow-tawk-connect`.
5. Check that password login and reset, staff invite creation and email, owner/staff/customer access, and booking and payments work for the expected accounts. Verify that an enrolled account completes the TOTP challenge, other tenants' objects stay inaccessible, and quota exhaustion returns HTTP 429 with a `Retry-After` header. Verify the recovery-code flow end to end: generate codes at AAL2, sign in with only the password at AAL1, consume one code, confirm authenticated surfaces open inside the 10-minute window and that the same code cannot be consumed twice. All clients that use the same Data API need to handle AAL2 for enrolled users, including any separately deployed mobile clients.

Shared endpoint quotas are fixed 10-minute windows per verified user. Staff invite email has separate owner-wide and per-invite quotas. The project-wide Data API check covers authenticated REST and RPC requests. Private account, booking, staff and payment-order tables also have restrictive RLS policies so their checks combine with existing owner, staff and customer policies.

## Distributed rate limiting (2026-11-26 hardening)

Node-side rate limiters no longer rely on per-process memory alone. `server/distributedRateLimit.ts` claims budget from the shared Postgres counter via `studioflow_edge_rate_limit_claim` (service-role only), using `sha256(purpose | scope | key)` bucket keys — no raw IP, user id or booking reference is stored. Behaviour:

- When the shared store is configured (`SUPABASE_SERVICE_ROLE_KEY`/`SUPABASE_SECRET_KEY` + the project URL), limits hold across serverless instances and cold starts. A configured-but-unreachable store **fails closed**: the route answers 503 `rate_limit_unavailable` with `Retry-After: 30`. Set `STUDIOFLOW_DISABLE_DISTRIBUTED_RATE_LIMIT=1` only as a deliberate escape hatch.
- When the store is not configured, a bounded per-process fallback keeps development working (logged once); production should always configure the service credential.
- `server/rateLimit.ts` is now an async middleware: verified callers get a per-user bucket with an `authenticatedMax` ceiling; anonymous callers are bucketed by the trust-proxy-aware client IP (spoofed `X-Forwarded-For` does not move the budget). Limited requests receive HTTP 429 with `Retry-After`, `RateLimit-Limit`/`RateLimit-Remaining`/`RateLimit-Reset` headers and `code: 'rate_limited'`.
- Booking email (5 per booking per 10 min) and the onboarding AI copier (30 per user per 10 min) claim from the same shared counter; both return 429 + `Retry-After`/`retryAfterSeconds` on exhaustion and fail closed (503) on store error.

## MFA recovery codes (2026-11-26 hardening)

`supabase/migrations/20261126143000_studioflow_mfa_recovery_codes.sql` adds `public.studioflow_mfa_recovery_codes` (no client-role grants; RLS on) holding only SHA-256(`salt` || ':' || `normalized code`) hashes with a per-code 32-hex salt, plus these RPCs:

- `studioflow_mfa_recovery_codes_issue(jsonb)` — `authenticated`, asserts `aal = 'aal2'`; stores 1–8 entries and atomically replaces all prior unconsumed codes for the caller.
- `studioflow_mfa_recovery_codes_count()` — `authenticated`; the caller's own unused count (drives the Account security "codes remaining" display).
- `studioflow_mfa_recovery_codes_consume(uuid, text)` — `service_role` only; normalization (strip non-alphanumerics, upper-case), per-account throttle of 10 attempts per 10 minutes via the shared claim RPC, then an atomic `UPDATE … consumed_at IS NULL` so two concurrent requests cannot both spend one code.
- `studioflow_mfa_recovery_active(uuid)` — `service_role` only; true for 10 minutes after a consumption (informational; the live enforcement path reads the same window inline).
- `prune_studioflow_mfa_recovery_codes()` — service-role housekeeping for codes consumed more than 30 days ago.
- `studioflow_private.mfa_session_allowed()` is replaced: a JWT with `aal = 'aal2'`, an account with no verified factor, **or** a consumed code within the last 10 minutes all pass. The Data API pre-request hook and every AAL2 RLS policy therefore open for exactly the recovery window and close again afterwards.

Because an AAL1 session is rejected by the pre-request hook, consume cannot run as an `authenticated` Data API call. The Node routes `POST /api/account/recovery-codes/consume` and `GET /api/account/recovery-codes/active` (re-exported for Vercel under `api/account/recovery-codes/`) verify the caller's bearer token first and then call the service-role RPCs. The user id always comes from the verified token, never from the request body. The browser generates codes (`src/lib/recoveryCodes.ts`), shows them once, and hashes them with WebCrypto before storage, so plaintext codes exist only in the browser at generation time. The MFA challenge (`src/components/AuthMfa.tsx`) offers "Lost authenticator? Use a recovery code"; after a successful consume the user has 10 minutes to reach Account security, enrol a fresh authenticator and remove the lost factor.
