### Lead-form security deployment blockers

- The Edge Function skips Turnstile when `TURNSTILE_SECRET_KEY` is empty. When it is set, it requires a valid `turnstile_token` on **both** public and trusted calls. The current demo dialog does not render a Turnstile widget or submit a token, and the same-origin fallback does not forward one. Setting the secret alone would reject those real submissions. A coordinated widget/site-key, token propagation, CSP, expiry/retry, accessibility and Cloudflare verification implementation and authorized deployment/QA are required before relying on Turnstile. Do not infer that production currently has it configured.
- **Lead limits (repository implementation, not deployed evidence):** the browser calls the Edge Function first; definitive 4xx responses including 429 do not trigger fallback. On an unavailable primary it can call `/api/nexora-demo-lead`, which atomically claims a 5-attempt/600-second fixed-window budget using the new service-role-only `claim_landing_lead_rate_limit` Postgres RPC before its trusted Edge call. The Edge claims a budget for direct public calls. Both use the same table, SHA-256 algorithm and defaults; the budgets are the **same only if** the project, stable salt and exact observed IP string match. Proxies, IPv6 representations and deployment configurations may produce different buckets. Counters are database-shared across instances, not per-process; Edge's cleanup trigger is per-instance and the server's cleanup is probabilistic/best-effort. The existing prune function removes rows only after they have been expired for over one hour; without a successful cleanup they can remain longer. Historical migration comments suggesting per-instance salts or deletion at window expiry are inaccurate; do not edit the already-applied migration. Configure scheduled pruning if retention policy requires it. Both fail closed if the database counter is unavailable (Edge 503, fallback 503); exceeded budget returns 429 and a Retry-After computed from the remaining window. Invalid fallback submissions and honeypot hits do not consume a budget; direct Edge validates after counting. Fixed windows allow bursts at boundaries and visitors behind a shared NAT can affect one another.
- **Release order and approval:** `20261125090000_nexora_lead_rate_limit_rpc.sql` is listed as pending in the repository migration ledger, not recorded as applied and not evidence of owner approval for production. In an approved staging environment, first reconcile migration history, apply the migration, verify the RPC and its privileges, and run multi-session load/expiry tests. Only after explicit production approval, apply the migration through the protected release process **before** deploying the updated lead Edge function and Vercel/Express server. The current production workflow deploys reviewed WhatsApp functions, not `submit-landing-lead`; arrange an authorized, targeted deployment separately. Deploying new code before the RPC exists fails closed with 503. Do not use deploy-only mode for this change before confirming the database prerequisite. Reconcile the history ledger after confirmed application so later remote history checks remain accurate.
- **Identity/trust:** Vercel uses `x-vercel-forwarded-for` (the peer that connected to Vercel); it can identify an upstream proxy instead of the visitor. Express uses `req.ip`: enable `TRUST_PROXY` only for verified proxy hops/ranges and prevent direct bypass, or visitors can spoof addresses. Without a valid address, the server shares an `unknown` bucket. Direct Edge uses the existing first `x-forwarded-for` entry (then `x-real-ip`); verify the actual Supabase gateway overwrites/sets these headers securely for this deployment, including upstream proxies and direct access. Until verified, the direct per-IP limiter and cross-path alignment are not guaranteed and may be spoofed or group visitors. [Vercel request headers](https://vercel.com/docs/headers/request-headers); [Supabase Edge example](https://supabase.com/docs/guides/functions/examples/cloudflare-turnstile). Configure the same high-entropy `LANDING_LEAD_RATE_LIMIT_SALT` in both runtimes without putting it in browser variables; the public default is predictable and hashed IPs are not anonymous. The new SQL migration must be applied before either updated handler is deployed; the old RPC remains available and uses the same table during a rolling update. Verify migration/RPC availability and grants before rollout; a failure blocks submissions. No configuration or deployment was changed here.
- **Low-friction checks:** a visually hidden, aria-hidden, untabbable named honeypot is silently acknowledged without storage. A two-second elapsed-time check is applied in the UI and to supplied values on both endpoints. The elapsed value is client-controlled and forgeable; missing values remain allowed for older clients, so it is not proof of human activity or a standalone bot barrier. Check keyboard/screen-reader behavior and autofill on a real device.
- Edge operational logs now use static messages for database/rate-limit failures and exceptions; mock tests verify secrets and contact details do not appear. Actual deployed Edge behavior remains unverified until the function is authorized for deployment and tested.
