# StudioFlow / Nexora — Salon Website Builder & Platform

AI-assisted salon website builder, owner workspace, public salon websites and the Nexora customer app (`/?app=1`), backed by Supabase (Auth, Postgres RPCs, Storage, Edge Functions).

## Quickstart

```bash
npm install
cp .env.example .env   # add GEMINI_API_KEY for live AI endpoints (optional)
npm run dev            # app + /api/* on http://localhost:3000
```

Production: `npm run build && npm start` (serves `dist/` plus `/api/*` from `dist/server.cjs`).
Static hosting (`.openai/hosting.json` → `dist/`): the UI stays fully usable; AI endpoints
(`generate-bio`, `generate-promo-image`, `generate-promo-copy`, `ai-recommendations`) degrade to
honest local fallbacks when the server is unreachable, and AI copy is only applied when the server
reports `"source": "ai"`.

### Automatic website and installed web-app updates

Each build emits a public `app-version.json` with the same UUID embedded in the JS bundle. The shared root update manager checks it without cache every 45 seconds while visible and on foreground/online events (throttled). A safe idle screen updates after a 5-second notice. Open dialogs, uploads, pending workspace saves, checkout and edited fields prevent automatic reload. The popup offers Update now or a five-minute defer; active modal/payment work must finish before applying.

Only the current URL's update markers change. Salon, app mode, referral, builder step, fragment, login and saved account data remain. No auth storage or caches are cleared. Offline/invalid version responses are ignored. An already attempted target cannot automatically loop. Existing tabs predating this feature need one fresh load to obtain the manager; future releases are detected by it. This covers browser and Chrome-installed PWA, not an Android APK store update.

Verification: `node scripts/verify-app-updates.mjs`; manifest UUID must occur in its HTML-linked JS. Live QA compares an idle customer tab and an open owner form across two actual publications.

### Device notifications for new releases
Customer app → Profile → Settings → **App update notifications** lets each device opt in or turn off release notifications. The update popup also offers the enable action. Browser permission is requested only on that button click. Granted permission plus the device opt-in are both required. New-release detection sends one notification per release, using the active service worker on Android; no customer details, passwords, referral/auth tokens or third-party notification endpoints are used. Clicking focuses existing work without navigating away from checkout; an unopened window opens the public same-origin route. Denied/unsupported browsers keep the in-app update notice.

These are notifications generated by the running release checker, not background Web Push. A completely closed app cannot discover releases until reopened; closed-app delivery needs a separate push subscription and trusted broadcast service. `node scripts/verify-update-notifications.mjs` checks permission handling, deduplication, delivery retry and safe notification-click routing without prompting a real device or sending notifications.
